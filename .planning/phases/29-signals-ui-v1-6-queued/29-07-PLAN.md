## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (unauthenticated or staff) → `/signals` route | The primary entry point this plan exposes — must be gated before any DB read |
| Browser (staff) → `/signals?practiceArea=&category=&status=&search=` query string → page.tsx's in-memory filter pass | Untrusted param values reach a plain JS `.filter()`, not a SQL query — no injection surface, but must not throw on malformed input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-07-01 | Spoofing | `/signals` page access | mitigate | `requireStaffAccess()` as the literal first statement, belt-and-suspenders alongside the `(dashboard)` route group's own layout gate (Pitfall 3 — this route lives in `src/app/(dashboard)/signals/page.tsx`, mirroring `/reviews`/`/settings`, not a standalone `src/app/signals/` tree with its own redundant layout) |
| T-29-07-02 | Denial of Service | Unbounded `Promise.all` fan-out (per-practice-area offering fetch × per-signal link-count fetch) | accept | At current seed scale (1 practice area, 39 signal rows, 11 offerings) this is ~50-90 fast indexed queries per page load — acceptable for an internal 3-partner tool; documented as a scale ceiling to revisit if a future practice area seed materially grows row counts (not a security vulnerability, a performance note) |
| T-29-07-03 | Tampering | Malformed/out-of-range `category`/`status`/`search` filter values reaching the in-memory `.filter()` | mitigate | A non-matching value simply yields zero rows (the existing `hasActiveFilters`-branched empty-state copy handles this gracefully) — never a thrown exception, since the filter predicates use safe string comparisons (`.includes()`, `===`) with no `eval`/dynamic-code paths |
