## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser URL -> `personas/page.tsx` `searchParams` | `selected` and filter params are user-controlled before `parseSelectedId`/`parsePersonaFilters` run |
| Browser URL -> `personas/[id]/page.tsx` `params`/`searchParams` | The dynamic `id` segment and any carried-over query params are user-controlled before being echoed into the redirect target |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-01 | Tampering | `personas/page.tsx`'s use of `parseSelectedId` before it reaches `PersonaList` -> `PersonaDetail` -> `getPersonaById` | mitigate | `parseSelectedId` (Plan 05-01, re-exported from `personaFilters.ts`) already returns `undefined` for non-numeric input; `PersonaDetail`'s existing `getPersonaById(id)` + `notFound()` path (unchanged this plan) handles a valid-but-nonexistent numeric id safely |
| T-5-02 | Spoofing / Tampering | `personas/[id]/page.tsx` redirect target | mitigate | Redirect target is always the hardcoded literal `` `/personas?${qs.toString()}` `` built from `URLSearchParams` — never a full user-supplied URL — so no open-redirect surface exists regardless of what values are echoed into the querystring |
| T-5-03 | Elevation of Privilege | `personas/page.tsx`, `personas/[id]/page.tsx` | mitigate | `await requireStaffAccess();` is preserved as the first statement in both routes' bodies through this consolidation/rewrite — never removed or made conditional |

</threat_model>
