First `useEffect`, dependency array `[selectedId]` only (never `children` — this is Pitfall 3's exact guard, re-firing on every unrelated filter/search re-render would jar-scroll the page): if `selectedId == null` or `!containerRef.current`, return; else `containerRef.current.querySelector<HTMLElement>('[data-row-id="' + selectedId + '"]')?.scrollIntoView({ block: 'start', behavior: 'smooth' })` — `block: 'start'` (not `'center'`) per D-06's explicit scroll-to-top-of-viewport requirement. Do not move focus in this effect — focus stays on the row per the Anti-Pattern note (breaks ArrowUp/ArrowDown continuity otherwise).

    Add a second `useEffect` (dependency array `[]`, cleanup via `removeEventListener`) that attaches, via `containerRef.current.addEventListener`, one `'click'` listener and one `'keydown'` listener at the container level (event delegation over the server-rendered `<tr>` children, since those rows can never carry their own `onClick`):
    - Obtain the setter via `const [, setSelected] = useSelectedRow();` called inside `ExplorerTableBehavior` itself (not inside the effect). Do NOT read the current `selected` value out of this tuple for use inside the delegated listeners — those listeners are attached once (dependency array `[]`) and would close over whatever `selected` was at mount time, going stale on every subsequent toggle (row 5 open -> click row 5 again would compare against the stale mount-time value instead of the live one and incorrectly re-open instead of collapse). Use nuqs's functional-updater form instead, which reads the live value at call time regardless of when the closure was created (verified in `node_modules/nuqs/dist/index.d.ts:376`).
    - `click` handler: `const rowEl = (event.target as HTMLElement).closest('[data-row-id]'); if (!rowEl) return; const id = Number(rowEl.getAttribute('data-row-id')); setSelected((old) => (id === old ? null : id));`
    - `keydown` handler: FIRST, before checking `event.key`, compute `const activeRowEl = (document.activeElement as HTMLElement | null)?.closest('[data-row-id]'); if (!activeRowEl) return;` — this guard is mandatory. `ExplorerTableBehavior`'s container wraps both the row list AND the expanded detail panel (which can contain focusable links, e.g. Arcpedia articles); without this guard, ArrowUp/ArrowDown/Enter fired while focus is inside the detail panel (not on a row) would wrongly `preventDefault()` and hijack focus away from the link the user is trying to activate normally. When `activeRowEl` is `null` (focus is inside the detail panel, not on a `[data-row-id]` row), the handler must no-op entirely: skip `preventDefault()` and make no focus/toggle change, letting the key event proceed with its default browser behavior. Only after this guard passes, branch on `event.key`: on `'Enter'`, same toggle logic as click, using `activeRowEl` as the row element and the same functional-updater form (`const id = Number(activeRowEl.getAttribute('data-row-id')); setSelected((old) => (id === old ? null : id));`), plus `event.preventDefault()`. On `'ArrowDown'`/`'ArrowUp'`, `event.preventDefault()`, read `Array.from(containerRef.current.querySelectorAll<HTMLElement>('[data-row-id]'))`, find the index of `activeRowEl` in that array (guard above guarantees it is non-null and present), compute the next index clamped to array bounds (no wrap-around per UI-SPEC), set the previously-focused element's `tabIndex = -1`, the new element's `tabIndex = 0`, then call `.focus()` on it.

    Render `<div ref={containerRef}>{children}</div>`.
