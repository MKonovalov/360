<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| schema.ts -> Neon Postgres | The pushed schema is the enforcement backstop for dedup (unique constraints) and rollback dependent-row detection (FK on import_log.batchId) — a schema-level gap here weakens every later plan's application-level logic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Tampering | company.domain / persona.email unique constraints | mitigate | DB-level unique constraints are the enforcement backstop for D-01/D-04's dedup key — even if a future application-layer bug attempts a duplicate-domain or duplicate-email insert, Postgres rejects it outright rather than silently creating a second row (Pitfall 2 in 07-RESEARCH.md, the "silently succeeds with two rows" failure mode) |
| T-07-02 | Tampering / Data Loss | import_log.batchId FK (no onDelete override, Postgres default NO ACTION) | mitigate | The default NO ACTION FK behavior means a company/persona row that has gained a dependent Signal or company_persona_role row after import cannot be deleted by rollback without an explicit dependent-check (Plan 07-05) — this schema-level constraint is the last-line defense described in RESEARCH.md Pattern 5 / Pitfall 4 |
| T-07-06 | Elevation of Privilege | No roles/permissions system (ACCS-01 deferred to v2) | accept | Any authenticated staff member can eventually import/rollback any batch once this schema lands — matches the project's existing binary access model, explicitly accepted per REQUIREMENTS.md, not a new gap introduced by this schema |
</threat_model>
