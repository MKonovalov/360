## Trust Boundaries

| Rollback -> live company/persona tables | findRollbackableRows/markRolledBack gate a genuinely destructive delete path — this phase's first real DELETE against production-shaped data |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Tampering | upsertCompanyByDomain/upsertPersonaByEmail silently overwriting a field with a blank value | mitigate | Both functions build their update patch exclusively via dedupKeys.ts's buildUpdatePatch, which drops undefined/empty-string entries — a blank CSV cell on a matched row can never null out an existing value, per D-10 |
| T-07-02 | Tampering / Data Loss | A company/persona gaining a dependent Signal or company_persona_role row between findRollbackableRows' pre-check and Plan 07-06's actual delete | accept | No transaction spans this gap (drizzle-orm/neon-http has no transaction support, verified in RESEARCH.md) — the import_log/dependent-table FK constraint (Plan 07-01) is the real backstop: a delete attempt against a row that gained a dependent mid-flight raises a Postgres 23503 error, which Plan 07-06 must catch and report as skipped, never let surface as an unhandled exception |
| T-07-06 | Elevation of Privilege | Any authenticated staff member can roll back any batch (no per-user restriction) | accept | Matches this project's existing binary access model (no roles system, ACCS-01 deferred to v2) — explicitly accepted in D-15, not a new gap this plan introduces |
</threat_model>
