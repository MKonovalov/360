## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Signal (practice area A) → Offering (practice area B) | A signal must never be linkable to an offering outside its own practice area — this is a business-logic integrity boundary, not a classic auth boundary, but it protects against a partner accidentally routing a signal to the wrong practice area's service catalogue |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-01 | Tampering / Information Disclosure | `insertSignalOfferingLink` | mitigate | Cross-practice-area link integrity threat (named explicitly in 30-RESEARCH.md Security Domain) — application-layer `practiceAreaId` equality check comparing the signal's practice area to the offering's practice area before any write; rejects with `practice_area_mismatch` rather than allowing a cross-boundary link. This is the single enforcement point — both the seed script (Plan 06) and future Phase 31/32 Server Actions call this same function, so the guard cannot be silently bypassed by a second, unguarded insert path |
| T-30-08 | Tampering | Small race window between the two reads (signal practice area, offering practice area) and the write (no `db.transaction()` — `neon-http` has none) | accept | Documented, accepted tradeoff matching `importBatches.ts`'s own precedent — the practical risk is negligible for a 3-partner internal tool with no concurrent-write load on this table, and a mismatched link (if it ever occurred via a race) is a data-quality issue correctable by a manual `deleteSignalOfferingLink` call, not a security breach |
</threat_model>
