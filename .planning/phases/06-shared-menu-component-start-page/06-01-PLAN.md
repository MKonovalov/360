<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client browser → recordView Server Action | Server Actions are directly callable HTTP endpoints even without a Route Handler; any client (including a malicious one bypassing the UI) can invoke `recordView(recordType, recordId)` directly |
| Dashboard query functions → Neon Postgres | All four stats.ts queries and the recentlyViewed upsert/list queries cross into the database layer with caller-supplied or derived parameters |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-01 | Spoofing / Tampering | `recordView` Server Action (`src/app/actions.ts`) | mitigate | `userId` is derived exclusively from `requireStaffAccess()`'s server-verified Clerk session; `recordView(recordType, recordId)` never accepts `userId` as a parameter, so a direct caller cannot write a `recentlyViewed` row under another user's identity |
| T-06-02 | Elevation of Privilege | `recordView` Server Action called by an unauthenticated client | mitigate | `requireStaffAccess()` is called first, before any DB access; an unauthenticated caller is redirected server-side and no write occurs |
| T-06-03 | Tampering | SQL injection via dashboard filter/threshold parameters (`stats.ts`) | mitigate | All new queries use Drizzle's parameterized query builder (`eq`, `gte`, `exists`, `count`) exclusively — no raw SQL string interpolation, consistent with `companies.ts`'s established convention |
| T-06-04 | Information Disclosure | `recordType` value accepted by `recordView` without DB-level constraint verification | accept | TypeScript union type (`'company' \| 'persona'`) constrains the value at the call boundary; the `recordTypeEnum` Postgres enum column additionally rejects any other value at the DB layer as defense in depth; a nonexistent `recordId` merely produces an orphaned tracking row, not a security issue |
</threat_model>
