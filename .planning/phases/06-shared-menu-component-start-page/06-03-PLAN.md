<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client browser (RecordViewTracker mount) → recordView Server Action | Every detail-panel mount (click, keyboard, or deep link) triggers a real write; this plan controls WHEN that trigger fires, not the write path itself (already mitigated in Plan 06-01) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-07 | Tampering / Information Disclosure | `RecordViewTracker` firing before a record is confirmed to exist | mitigate | Task 2 places `RecordViewTracker` strictly after the `notFound()` guard in both `CompanyDetail` and `PersonaDetail`, using the confirmed `company.id`/`persona.id` — a nonexistent/deleted id can never produce a `recentlyViewed` row (RESEARCH.md Pitfall 4) |
| T-06-08 | Denial of Service (minor) | `recordView` fired repeatedly by rapid row-toggling (open/close/open) | accept | Each call is a single parameterized upsert (`onConflictDoUpdate`), fire-and-forget with an empty catch — worst case is redundant `viewedAt` updates, not a correctness or availability issue, and Postgres upsert is cheap at this record volume |
| T-06-09 | Information Disclosure | Disabled Menu items (Import/Analyze) visible to any signed-in user with no functional access | accept | Both items are inert `disabled` placeholders this phase — no data or action is exposed; matches the project's existing "any authenticated staff = full visibility" access model |
</threat_model>
