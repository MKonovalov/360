## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Delete confirmation UI → deleteXAction (via caller-supplied onDelete) | The one place in this phase where a genuinely irreversible write is triggered from the client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-06-01 | Repudiation/Integrity | DeleteGuardDialog's blocked-state refusal | mitigate | The blocked branch renders NO confirm/delete button at all — there is no UI path to retry the delete from this dialog once blocked; the user must close it, and the underlying `deleteXAction` re-checks `hasXDependents()` fresh on every call regardless, so even a hypothetical stale-UI bypass would be re-rejected server-side |
| T-30-06-02 | Elevation of Privilege | Generic `onDelete`/`onArchive` callback props | accept | These dialogs never decide WHICH entity/id to act on — that decision and the `requireStaffAccess()` gate both live in the Server Action the caller's callback wraps (30-02/30-03), so this component genuinely cannot be misused to delete/archive anything the caller didn't already scope the callback to |
| T-30-06-03 | Tampering | TriggerEditor's `offeringId` prop | accept | Supplied by the parent (Matrix row), never user-editable in this component — the value flows straight into `createTriggerAction`'s zod-validated `offeringId: z.number().int().positive()` field, and a tampered id server-side still resolves through the DB's FK constraint on `trigger.offering_id` |
</threat_model>
