<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Reorder button clicks → reorderXAction | Client computes the new order locally from already-fetched data, then persists via a staff-gated Server Action |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-08-01 | Tampering | Client-computed reorder array | mitigate | `reorderXAction` recomputes positional sortOrder purely from array INDEX (i-th id gets sortOrder=i), so even a maliciously-crafted id array can only reorder rows the client already had legitimate read access to via the same staff-gated page — it cannot inject an id belonging to a different, unrelated entity into another entity's sort sequence since each reorder action only ever writes to the ONE table it's scoped to |
| T-30-08-02 | Elevation of Privilege | Domain rows correctly omitting Archive | mitigate | This is a data-integrity/UX correctness concern more than security, but omitting a nonexistent status transition prevents a confusing dead client-side action that would otherwise silently fail server-side (there is no `archiveDomainAction` to call) |
</threat_model>
