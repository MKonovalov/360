<domain>
## Phase Boundary

The committed catalog snapshot (`src/lib/models/catalog.json`) ships current NousResearch rows and a refreshed OpenCode roster, generated by an extended dev-time refresh script. The script gains a NousResearch source (anonymous `GET https://inference-api.nousresearch.com/v1/models`, 292 rows), converts Nous pricing per-token → per-MTok (×1e6), live-joins `supported_parameters` to `structuredOutputs` (throws-not-degrades), derives Nous `family` from the id prefix, and regenerates the snapshot with the new `nousresearch` rows + a refreshed Go roster (17 → 25 live rows). Zen/Go rosters are roster-verified per the D-02 doctrine; the Zen-wins dedup survives regeneration (already expressed once in the registry via `dedupeProviderRows` from Phase 23 — the refresh script stays format-only per D-23-08).

**What this phase is NOT:** no run-path/instantiation changes (Phase 25), no Settings UI (Phase 26), no verification gate (Phase 27), no `@ai-sdk/openai-compatible` installation (Phase 25). No changes to `getProviderForModelId` priority order, gates, or the registry logic itself (Phase 23 delivered those) — this phase is DATA: the script + the regenerated snapshot + the canaries that lock the new data shape.

<decisions>
## Implementation Decisions

### NousResearch Snapshot Scope (CAT-01)
- **D-24-01:** The snapshot ships **ALL 292 live NousResearch roster rows** with `providerID: 'nousresearch'` — the full catalog is the menu, the Hermes-pair allowlist (D-23-05) is the gate. Matches the D-02 openrouter precedent (336 rows ship; gates control servability). Snapshot grows by ~292 rows; Phase 26 union picker sees the full set; future allowlist expansion needs no re-refresh.
- **D-24-02:** Nous rows map `api.url = https://inference-api.nousresearch.com/v1` and `api.npm = @ai-sdk/openai-compatible` per CAT-01.

### Snapshot Restructure (deviates from v1.5 "no schema change" roadmap note)
- **D-24-03:** `catalog.json` is **restructured from flat `{ generatedAt, models: [...] }` to grouped `{ generatedAt, providers: { nousresearch: [...], anthropic: [...], openrouter: [...], opencode: [...], ... } }`** — a deliberate, user-confirmed deviation from the v1.5 roadmap footnote's "no schema change" (which applies to the DB schema; this changes the snapshot FILE shape only). The DB schema doctrine stays intact (provider identity still derived from the catalog, never persisted).
- **D-24-04:** ALL consumers migrate in the SAME change as the restructure (the 19-01 "all callers migrate in the same change so next build stays green" doctrine): `src/lib/models/catalog.ts` registry (reads `models` array), every test fixture and canary in `catalog.test.ts` that reads the live snapshot, Phase 23's count-stability/no-flip/hermes canaries, and future Phase 25/26/27 consumers that parse the snapshot. Green build after the single change — no intermediate broken state.
- **D-24-05:** The provider grouping key matches the **snapshot `providerID` values** (`nousresearch`, `opencode`, `opencode-go`, `openrouter`, `anthropic`, plus the other vendor IDs currently present — kilo, vercel, google, openai) — NOT the registry `ModelProviderId` union. The registry's `'opencode'` logical-provider mapping over `opencode` + `opencode-go` snapshot IDs is unchanged (Phase 23 logic); the restructure is a faithful regrouping of the same rows by their existing `providerID` field.

### Go Roster Verification (CAT-04, D-02 doctrine)
- **D-24-06:** The refresh script **live-fetches the Zen (60) + Go (25) `/v1/models` endpoints and compares id-sets against the CLI-parsed roster** — any drift fails loudly BEFORE writing, so the committed snapshot stays usable (throws-not-degrades, same doctrine as the OpenRouter structured-output join). Regeneration is Go 17 → 25 live rows.
- **D-24-07:** Drift semantics = **strict** — ANY difference between the live Zen/Go id-set and the CLI-parsed id-set aborts the run (a single new model OpenCode adds blocks refresh until the CLI catches up or the script re-runs). No count-only tolerance, no warn-on-extra leniency.

### `~latest` Alias Handling (D-04 doctrine)
- **D-24-08:** All 11 Nous `~latest` alias rows **ship verbatim in the snapshot** (never stripped — D-04), with `providerID: 'nousresearch'`. They self-exclude from servable (the Hermes allowlist pins concrete ids, D-23-05). Matches the D-02 openrouter precedent (`~latest` INCLUDED but labeled).
- **D-24-09:** No explicit alias flag field — the `~latest`-ness is **derivable from the id string** at render time (Phase 26 labels it). Zero extra field on the restructured rows.

### Refresh Atomicity
- **D-24-10:** The refresh remains **ONE atomic command** (`npm run models:fetch`): shell opencode CLI (existing), fetch OpenRouter structured-outputs (existing), fetch Nous roster (new), fetch Zen/Go rosters + drift check (new), regroup by provider (restructure), write catalog.json. Any failure aborts WITHOUT writing — the committed snapshot stays usable. No per-source subcommands that could leave a partially-refreshed snapshot.

### Post-Refresh Canary Re-lock (D-23-02, CAT-04)
- **D-24-11:** The count-stability (39 post-dedup servable) and roster-shape canaries from Phase 23 are **re-locked to the NEW explicit numbers in the SAME commit as the regenerated snapshot** — a deliberate, reviewed re-lock per the D-02 roster-verify doctrine. The canaries keep hardcoded expected counts (NOT auto-derived from the committed snapshot — that would defeat their purpose of catching unintended shape changes).
- **D-24-12:** A **full NousResearch canary group** ships in `catalog.test.ts` covering: ~292 rows present with `providerID: 'nousresearch'`; Hermes allowlist rows servable through the gate (D-23-05 pins resolve); pricing ×1e6 conversion correct (per-token `0.0000016` → `1.6` per-M — research Pitfall 2); `family` derived from id prefix (`nousresearch/hermes-4-*` → `hermes`); ~latest aliases present + self-excluded from servable. Mirrors the existing dual-canary (fixture + live-snapshot) convention.

### Claude's Discretion
- Exact structure of the grouped snapshot (e.g. `providers` object keyed by providerID; whether `generatedAt` stays top-level or moves) — must satisfy D-24-03/04/05 and keep a single source of truth.
- Whether the Zen/Go drift check reports per-id diffs in the error message (recommended: yes, for debuggability).
- Naming for the new `fetchNousRoster()` / `fetchZenGoRosters()` functions — consistent with `fetchOpenRouterStructuredOutputs()` in the existing script.
- How the grouped-snapshot migration is sequenced within the plan's tasks — must keep the build green at every commit (D-24-04).
- Whether Nous `family` derivation handles edge cases beyond `hermes-4-*` (e.g. other families in the 292-row roster) — derive from id prefix per CAT-03, exact prefix table is planner's call.

## Existing Code Insights

### Reusable Assets
- `fetchOpenRouterStructuredOutputs()` in `refresh-model-catalog.ts` — the throws-not-degrades live-fetch pattern (fetch → non-OK throws → abort without write) to mirror for the Nous roster and Zen/Go drift checks.
- `parseModels` / `trimRecord` — the deterministic parse + trim pipeline; Nous rows flow through the same `trimRecord` field contract (id, providerID, name, family, status, api{npm,url}, cost{input,output}, limit{context,output}, structuredOutputs).
- `catalog.test.ts` dual-canary convention (fixture + committed-snapshot) — template for the full Nous canary group (D-24-12).

### Established Patterns
- Throws-not-degrades: any live-source failure aborts WITHOUT writing — the committed snapshot stays usable (Pitfall 3, CAT-02).
- Roster-verify doctrine (D-02): every allowlist/default/count must be verified against the live roster or committed snapshot; count drift fails loudly and is re-verified intentionally.
- Raw ids pass VERBATIM (D-04) — `~latest` aliases ship, never stripped.
- scripts/ placement doctrine: `child_process` + `fetch` never enter `src/` (Phase 18 verification gate greps zero `exec|spawn|child_process` in src/).

### Integration Points
- `catalog.json` — restructured to grouped shape (D-24-03); every consumer migrates in the same change (D-24-04).
- `catalog.ts` — registry reads the grouped snapshot; the `'opencode'` logical-provider mapping over `opencode` + `opencode-go` snapshot IDs is UNCHANGED (Phase 23 logic).
- `catalog.test.ts` — canary re-lock (D-24-11) + new full Nous canary group (D-24-12).
- Phase 25 run path — reads the regenerated snapshot rows (nousresearch rows + refreshed Go roster) for instantiation.

## Specific Ideas

- The snapshot is the menu, the gate is the lock — shipping all 292 Nous rows means Phase 26's picker and Phase 25's run path see a complete, future-proof menu, and the Hermes allowlist (Phase 23) does the servability filtering.
- The grouped restructure is a deliberate readability + organization improvement the user explicitly confirmed despite the migration cost — the build must stay green through the single migration change (D-24-04).
- Strict drift semantics on Zen/Go (any diff aborts) is the most conservative reading of the D-02 roster-verify doctrine — refresh fails loudly rather than shipping a silently-stale roster.
