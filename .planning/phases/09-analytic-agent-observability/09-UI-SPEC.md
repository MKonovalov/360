# Phase 9 — UI Design Contract

> Visual and interaction contract for the Analytic Agent + Observability phase (Menu → Analyze web-search signal-detection agent with a human-reviewed proposal queue, plus Langfuse tracing and correction-reason capture). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Inheritance notice:** The design system (shadcn preset, typography scale, spacing scale, base color palette, copywriting voice) is inherited verbatim from `02/03-UI-SPEC.md` (Explorers), `05-UI-SPEC.md` (Layout Rework), `06-UI-SPEC.md` (Menu + Start Page), and `07-UI-SPEC.md` (CSV Import), confirmed against currently-shipped code (`src/app/globals.css`, `components.json`, `src/components/ui/*.tsx`, `src/components/companies/company-detail.tsx`, `src/components/enrichment/enrichment-review-dialog.tsx`, `src/components/layout/app-sidebar.tsx`). This document does **not** re-derive spacing/typography/base-color — it adds the genuinely new surfaces this phase introduces: (1) wiring the reserved Menu → Analyze slot live (currently a `disabled` item inside `EnrichMenu`, `enrichment-review-dialog.tsx:177`), (2) a synchronous-run feedback strip in the Company detail panel (running / success / fail-loud failure / already-covered), (3) a pending-proposal count badge on the Company detail panel (ANLZ-04), (4) a dedicated review queue page with evidence-inline proposal cards and Accept/Reject (ANLZ-02/03), and (5) the correction-reason capture dialog on Reject (OBSV-02).

**Two discretionary decisions resolved by the researcher (flagged for confirmation — see note at the end of the Interaction Contract):**
1. Review-queue placement: **dedicated top-level `/reviews` route + "Reviews" sidebar item** (CONTEXT.md D-12's stated preference: "prefer a route consistent with the app's explorer patterns"; ANLZ-03's wording "listing all pending proposals" is a global queue, not a per-company drill-down).
2. Proposal strength display: **neutral text label, not color-coded** — extends the `SignalBadge` "no per-type hue" lock (signal-badge.tsx comment) to the strength dimension; zero new hues.

## Color

Inherited verbatim (slate neutrals + indigo-600 accent + amber attention + token-driven destructive):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | white / slate-50 (`#f8fafc`) | Page background, proposal-card surface, run-status strip surface, review-queue empty state |
| Secondary (30%) | slate-100 / slate-200 (`#f1f5f9` / `#e2e8f0`) | Card/table borders, proposal-card divider between evidence block and footer, sidebar nav badge background, dropdown-menu content background+border |
| Accent (10%) | indigo-600 (`#4f46e5`) | Focus rings, inline text links (proposal-card Company name, "Review {N} proposals", "View trace" link), the new "Reviews" sidebar nav item's active-state highlight (`data-active:bg-indigo-50 data-active:text-indigo-600`, same treatment as Start/Companies/Key Personas) |
| Destructive | shadcn `--destructive` token (CSS-variable-driven per `globals.css` — resolves to standard red) | The correction dialog's confirm button ("Reject proposal", `Button variant="destructive"`) — the phase's one terminal/irreversible action. Never hand-rolled as a hardcoded `red-*` class (Phase 7 contract rule). Error **message text** is `text-red-600`, the pattern already established by `enrichment-review-dialog.tsx:196` (this is error copy, not a destructive-action surface — same distinction as Phase 7) |

Accent reserved for: focus-visible rings, inline text links, and the active sidebar nav-item highlight. **Never** apply accent to: the Analyze menu item, the run-status strip (informational — success is slate-900 neutral, mirroring Phase 7's "success is informational" rule for the Done step's `CircleCheckIcon`), the pending-count badges (amber — see below), or strength/R/C text (slate-500).

**Amber reuse — count badges (extending, not breaking, the SignalBadge lock):** the pending-proposal count badge on the Company detail panel and the "Reviews" sidebar badge use the app's established attention hue `amber-100` bg / `amber-800` text (the exact `SignalBadge` recipe in `src/components/companies/signal-badge.tsx`). Rationale: amber is this app's "needs attention" semantic (SignalBadge, warning banners, Needs Attention widget) and a pending proposal awaiting review is precisely an attention item. The lock that matters — **no per-signal-type hue, no per-strength hue** — is preserved: signal types keep the single `SignalBadge`, and strength/R/C render as neutral slate-500 text.

**Researcher decision (flagged):** proposal strength (low/medium/high) is **not** color-coded. A high-strength proposal looks identical in hue to a low-strength one; only the Label-size word distinguishes them. This is a deliberate extension of the project's "no new design language" constraint (CONTEXT.md Claude's Discretion) and the `SignalBadge` hue-lock. If the reviewer wants glanceable strength triage later, it is a small, contained change — but it would introduce the app's first red non-destructive use and a second badge dimension, so it is not defaulted in.

Second semantic color: none new. Success is informational (slate-900); failure is `text-red-600` error copy; the destructive token covers only the terminal Reject confirm.

## Interaction Contract (new this phase)

**Focal point:** On the Company detail panel, the Analyze flow is a *quiet utility* — the menu trigger stays in the top-right ghost-button group (never competing with the panel header), and the run-status strip is a slim, dismissible-by-refresh notice, not a modal. On the `/reviews` page, the anchor is the proposal-card list itself — evidence inline (per ANLZ-03), nothing behind a click except the two review actions.

### 1. Menu → Analyze wiring (detail panel)

| Behavior | Contract |
|----------|----------|
| Trigger | The existing `EnrichMenu` dropdown's `disabled` "Analyze" item (`enrichment-review-dialog.tsx:177`) becomes live: enabled when `canAnalyze` (all of `ANTHROPIC_API_KEY`, `FIRECRAWL_API_KEY`, `LANGFUSE_*` present in `env.ts`), disabled with "Analyze — Agent not configured" otherwise (D-15). | Behavior | Contract |

## Note on flagged decisions

Two discretionary choices were resolved by the researcher because the interactive question flow was unavailable in this session; both have clear recommended paths grounded in upstream artifacts, and both are cheap to override at planning time:

1. **Review-queue placement = dedicated `/reviews` route + sidebar item** (vs. per-company detail-panel section). CONTEXT.md D-12 explicitly prefers a route consistent with explorer patterns; ANLZ-03 says "dedicated review queue listing all pending proposals" (global). Override cost: low if planning disagrees — the card component and correction dialog are placement-agnostic.
2. **Strength = neutral text** (vs. color-coded badges). Extends the SignalBadge hue-lock; zero new hues. Override cost: low — a strength→badge-class map in the proposal card only.
