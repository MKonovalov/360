**For:** Claude Code implementation in the existing ArcLumen 360 codebase
**Location in app:** `Manage > Reviews` menu, two new items — `Signals` and `Offerings`
**Status:** Draft for review — framework-agnostic (this spec does not assume a specific stack; adapt file paths, routing, ORM syntax, and naming to the conventions already in use in the target repo)

## 0. How to use this spec

This spec was written without access to the actual ArcLumen 360 repository, so it is deliberately **framework- and stack-agnostic**: it defines the data model, business rules, UI behavior, and API contract, not file paths or ORM-specific code. Before implementing:

1. Map the entities in Section 2 onto the existing schema conventions (naming, ID types, timestamp/audit columns, soft-delete pattern, migration tooling) already used elsewhere in the app.
2. Match the UI components in Section 4 to the existing design system / component library rather than introducing new patterns.
3. Follow the existing auth/permission model for who can create, edit, and delete records (Section 5 states the minimum requirement only).
4. Flag any place where this spec's assumptions conflict with how `Manage` or other existing menu sections are actually built, rather than silently reconciling — surface it for a decision.

**Read Section 6 (Build Sequencing) before starting.** The user's stated priority is to build Signals first, but Signals has a hard data dependency on two lookup entities that structurally belong to the Offerings feature (Buyer Role, and optionally Offering itself). Section 6 proposes a sequencing that honors "Signals first" for the *user-facing feature* while resolving that dependency — read it before writing migrations.

## 1. Background & scope

ArcLumen Partners is a boutique GBS/operating-model transformation consultancy with a six-practice-area service portfolio (Portfolio → Practice Area → Domain → Offering → Engagement — the firm's locked naming taxonomy). Each of the firm's service catalogues already documents, per offering, an **Entry Trigger** (the business situation that makes a client receptive) and a **Primary Buyer** (the sponsoring role). This spec turns that structure into two manageable features inside ArcLumen 360:

- **Offerings** — lets a partner manage the Service Portfolio hierarchy (Practice Area → Domain → Offering) and, for each offering, its Triggers and Primary Buyers — replacing the current source of truth (Word-document catalogues) with a structured, queryable store.
- **Signals** — lets a partner define reusable **Company-level** and **Persona-level buying signals**, independent of any single offering, and link each signal to the Practice Area(s) / Offering(s) it's evidence for. This is the layer that sits *upstream* of the catalogue's own Entry Trigger text — a signal is something observable about a prospect (a trigger event, a persona's tenure, a public statement) that a partner uses to decide a hypothesis is worth testing.

**Explicitly out of scope for this spec:** the Hypotheses feature (a later milestone — hypotheses will consume Signals + Offerings but are not built here), any outreach/LTS integration, and any automated signal detection (this spec covers manual CRUD only — a partner records signals they've observed; nothing here scrapes LinkedIn or news feeds).

**Seed scope:** only one practice area — **GBS — Design, Build & Run** — is seeded with real data (Section 7). The data model must support all six practice areas from day one; the other five simply start empty.

## 2. Data model

All entities below need: a primary key, `created_at`/`updated_at`, `created_by`/`updated_by` (user reference), and a `status` field where noted. Use whatever ID and audit-column convention the existing schema already uses.

**`practice_area`**
| Field | Type | Notes |
|---|---|---|
| `name` | string | e.g. "GBS — Design, Build & Run". Unique. |
| `short_code` | string | e.g. `GBS`. Short, stable identifier for cross-references and URLs. Unique. |

**`domain`**
| Field | Type | Notes |
|---|---|---|
| `practice_area_id` | FK → practice_area | Required. |
| `name` | string | e.g. "Design", "Build", "Run". |

Domain is optional per the firm's own taxonomy ("applies where a practice area is naturally organised as a journey; practice areas without that structure go straight from Practice Area to Offering"). An `offering` may therefore have a null `domain_id`.

| `sort_order` | integer | |
| `status` | enum: `active`, `draft`, `retired` | |

|---|---|---|
| `name` | string | e.g. "CFO", "Head of GBS", "COO", "Transformation Sponsor". Unique. |
| `description` | text, nullable | |

### 2.2 Signals feature entities

**`company_signal`**
| Field | Type | Notes |
|---|---|---|
| `practice_area_id` | FK → practice_area | Required — every signal is scoped to a practice area first. |
| `name` | string | Short label, e.g. "No existing GBS/SSC". |
| `category` | string (free text, with autocomplete suggestions from existing values) | Seed categories for GBS: GBS-state, Financial & commercial, Organizational & restructuring, M&A & structural, Technology & ERP, Automation & AI maturity, Public content & intent, Geographic. Do not hardcode as an enum — other practice areas will need different categories (see Section 7 gap note). |
| `description` | text | The signal itself, in the observable form a partner would recognize it (e.g. "No visible 'Global Business Services' or 'Shared Services' entity in the group structure despite qualifying size and multi-country footprint"). |
| `status` | enum: `active`, `draft`, `retired` | |

**`persona_signal`**
| Field | Type | Notes |
|---|---|---|
| `practice_area_id` | FK → practice_area | Required. |
| `buyer_role_id` | FK → buyer_role | Required — reuses the same lookup as Offerings, so a persona signal is always tied to a real, manageable role, not free text. |
| `name` | string | Short label, e.g. "Newly appointed with prior GBS-build experience". |
| `category` | string (free text, autocomplete) | Seed categories: Tenure/mandate, Public conviction, Career pattern, Org/hiring signal, Content engagement. |
| `description` | text | |
| `status` | enum: `active`, `draft`, `retired` | |

**`signal_offering_link`** (join table — links a signal to the specific offering(s) it's evidence for)
| Field | Type | Notes |
|---|---|---|
| `signal_type` | enum: `company`, `persona` | |
| `signal_id` | integer | References `company_signal.id` or `persona_signal.id` depending on `signal_type` (polymorphic — if the framework's ORM doesn't support this cleanly, use two separate join tables, `company_signal_offering` and `persona_signal_offering`, instead — pick whichever matches existing conventions in the codebase). |
| `offering_id` | FK → offering | Must belong to the same `practice_area_id` as the signal — enforce at the application layer if not enforceable in the DB. |
| `relevance_note` | text, nullable | Optional short note on *why* this signal points to this offering (useful when a signal maps to more than one offering with different rationale each). |

A signal can link to zero, one, or several offerings within its practice area. Zero is valid — a partner may record a signal before deciding which offering it routes to.

## 3. Business rules

- A signal's `practice_area_id` constrains which offerings it can link to (see `signal_offering_link` note above) — the UI should filter the offering picker to the selected practice area, not show all offerings firm-wide.
- Deleting a `practice_area`, `domain`, `offering`, or `buyer_role` that has dependent records (offerings, triggers, buyer-role links, signals, signal-offering links) should be blocked or require explicit cascade confirmation — never a silent cascade delete, given this data underpins live outreach decisions.
- `status = draft` records should be excluded from any picker/dropdown used elsewhere (e.g. a draft offering shouldn't appear in the Signals linking UI) but still visible/editable in the Offerings management screens.
- No numeric pricing field on `offering` — see Section 8. Do not let Claude Code infer or invent one from the commercial-model text.

## 4. UI / IA

### 4.1 Menu placement

Under the existing `Manage` menu, `Reviews` submenu, add two new items:

- `Manage > Reviews > Signals`
- `Manage > Reviews > Offerings`

Match the existing visual and interaction pattern of whatever else lives under `Reviews` today (list/table conventions, filter bar placement, create/edit as modal vs. full page, etc.) — do not introduce a new UI pattern for these two screens.

### 4.2 Signals screen

Two tabs: **Company Signals** and **Persona Signals**. Each tab is a filterable list view.

**List view (both tabs):**
- Filter bar: Practice Area (dropdown, all six listed, defaults to showing all but with GBS pre-selectable since it's the only populated one initially), Category (dropdown, populated from distinct existing values), Status, free-text search over name/description.
- Table columns — Company Signals: Name, Category, Practice Area, Linked Offerings (count, expandable), Status, Last updated. Persona Signals: same, plus Buyer Role column.
- Row action: edit (opens form), archive (sets status to `retired`, does not hard-delete).
- Primary button: "New Company Signal" / "New Persona Signal".

**Create/edit form — Company Signal:**
- Name (required, short text)
- Practice Area (required, select)
- Category (required, autocomplete/free text with existing values suggested)
- Description (required, textarea)
- Linked Offerings (multi-select, options filtered to the selected Practice Area's active offerings; empty allowed)
- Status (select: active/draft/retired)

**Create/edit form — Persona Signal:**
- Same as above, plus:
- Buyer Role (required, select from `buyer_role` — with an inline "manage buyer roles" link/shortcut to the lookup management panel described in 4.3, so a partner isn't blocked if the role they need doesn't exist yet)

### 4.3 Offerings screen

Two tabs: **Service Portfolio** and **Offering × Trigger × Buyer Matrix**.

**Tab 1 — Service Portfolio:**
A hierarchical manager for Practice Area → Domain → Offering.
- Left panel or top-level list: Practice Areas (6, in sort order), each expandable to show its Domains (if any) and Offerings.
- CRUD at each level: create/edit/reorder/archive Practice Area, Domain, Offering.
- Offering edit form includes: Name, Practice Area, Domain (optional, filtered to the chosen Practice Area's domains), Offer Type, Description, Commercial Model Text, Buyer Roles (multi-select with rank/order — reuses `buyer_role` lookup), Status.
- Drag-to-reorder within a level (sort_order), consistent with however reordering is handled elsewhere in the app if a pattern already exists.

**Tab 2 — Offering × Trigger × Buyer Matrix:**
A table view, filterable by Practice Area (defaults to GBS), read-optimized but editable inline or via a side drawer:
- Rows: Offerings, grouped by Domain (matching the reference document's presentation — Design / Build / Run groupings with a section header per domain).
- Columns: Offering name, Trigger(s) (list, each editable/removable, "+ add trigger"), Primary Buyer(s) (the ranked `buyer_role` list, editable), Commercial Model (text).
- A visible "Manage Buyer Roles" action opens a small lookup CRUD panel (name + description only) — this is the one place buyer roles are created/edited/archived, referenced from both Offerings and Signals.

### 4.4 Cross-linking

From an Offering's detail view (Tab 1), show a read-only list of Company/Persona Signals currently linked to it (reverse lookup via `signal_offering_link`), so a partner can see, e.g., "which signals currently point to the GBS Maturity & Readiness Assessment" without leaving the Offerings screen.

## 5. Permissions (minimum requirement)

All three partners can create, edit, and archive Signals and Offerings records — this is a small internal tool for three co-founders, not a role-gated enterprise system. Record `created_by`/`updated_by` for accountability, but do not build a review/approval workflow for this milestone. Match whatever auth pattern (session, role check, etc.) the rest of `Manage` already uses.

## 6. Build sequencing (read before implementing)

The user's stated priority is "build Signals first." Taken literally, this is not fully buildable in isolation: a Persona Signal requires a `buyer_role` to reference, and both Company and Persona Signals are far more useful with real `offering` records to link to — both of those entities are structurally part of the Offerings feature (Section 2.1).

Recommended sequencing that honors "Signals first" as a *feature-delivery* priority without building on an empty foundation:

1. **Milestone 1a — shared data model + seed data.** Implement all tables in Section 2 (both Offerings and Signals entities) in one migration, and load the seed data in Section 7 (GBS practice area: domains, offerings, triggers, buyer roles, company signals, persona signals, and the links between them). No UI yet.
2. **Milestone 1b — Signals UI.** Build the Signals screens (Section 4.2) against the seeded data. This is the user-facing "Signals feature" and ships first, as requested.
3. **Milestone 1c — Offerings UI.** Build the Offerings screens (Section 4.3), shipping shortly after. Until this ships, the Service Portfolio and Trigger/Buyer data exist (from 1a) and are usable by Signals, but aren't yet editable through a UI — if that gap is unacceptable, ship 1c together with 1b instead of after it.

If the user wants Signals' UI to ship with genuinely nothing else built (no seed data, no buyer-role lookup), flag that the Practice Area picker and Persona Signal's Buyer Role field will have nothing to select from on first load, which likely isn't the intended experience — worth confirming before Claude Code starts.

## 8. Open items / decisions needed before or during build

- **Commercial figures.** Offerings have no numeric price field by design — five of six catalogues explicitly defer pricing, and only the Technology catalogue states a day-rate band (€2,500–3,500, 60–70% margin target). Confirm whether that's deliberate (Technology further along commercially) before adding pricing fields anywhere.
- **GBS / Technology boundary.** "Automation & AI Portfolio Governance & Benefit Realisation" appears in both the GBS and Technology catalogues with an explicitly unresolved scope boundary in the source documents ("technical assurance" vs. "benefit governance"). This spec seeds it once, under GBS only — resolve the boundary before seeding the Technology practice area, or the same offering name will exist twice with overlapping meaning.
- **Category taxonomy.** Company/Persona Signal `category` is free text with autocomplete rather than a fixed enum, because the eight GBS company-signal categories are unlikely to transfer unchanged to, e.g., M&A Diligence & Integration (which runs on deal-stage rather than tenure). Revisit once a second practice area is seeded — if categories converge, consider promoting to a proper lookup table at that point.
- **Dual-persona scoring.** Not part of this spec (belongs to the Hypotheses milestone), but noted here because it affects whether `persona_signal` eventually needs a "requires co-occurring signal" relationship — worth keeping in mind so this schema doesn't need a breaking change later.
- **Repository conventions.** This entire spec needs a pass against the actual ArcLumen 360 codebase (naming conventions, existing base entities, component library, routing pattern) before Claude Code starts — Section 0 flags this; it bears repeating here as a hard gate, not a suggestion.
