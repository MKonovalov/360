# Project Research Summary

**Project:** ArcLumen 360 (internal staff demand-gen tool)
**Domain:** Multi-provider AI model configuration — adding OpenRouter as a second AI provider alongside Anthropic (provider selector, provider-scoped primary picker, cross-provider fallback chains, provider-aware run path)
**Milestone:** v1.4 (continues from v1.3's Phase 18; v1.4 = Phases 19–22)
**Researched:** 2026-08-02
**Confidence:** HIGH overall — STACK verified against the live OpenRouter API + packed npm tarball; FEATURES/ARCHITECTURE/PITFALLS are codebase-grounded (on-disk source + committed catalog.json + v1.3 decision records); MEDIUM only where flagged (ecosystem UX norms, one SDK-version drift)

## Executive Summary

v1.4 adds OpenRouter as a second AI provider on the v1.3 model-settings foundation. All four research files converge on the same shape: **one new runtime dependency** (`@openrouter/ai-sdk-provider@^3.0.0`, peer-verified against installed `ai@7.0.45` + `zod@4.4.3`, engines `node >=22` — STACK HIGH), a **provider registry in `catalog.ts`** (gate-by-provider data map, union servable set, servable-scoped id→provider lookup), a **new `modelFactory.ts` seam** that is the only module importing provider SDKs (replacing the hardcoded `modelChain.map((id) => anthropic(id))`), a **provider selector + union-scoped fallback pickers** in Settings, a **chain-aware env gate** (per-provider key check at entry, D-15 mirror), and a **verification gate** (Phase 22). The committed snapshot already contains all 336 OpenRouter rows (`api.npm: '@openrouter/ai-sdk-provider'`, `providerID: 'openrouter'`) — **no catalog data refresh needed; v1.4 is a code change, not a data change**.

The four files conflict on five points, and the evidence is lopsided on most. **Recommendation set (details in Conflicts section): pass OpenRouter ids verbatim (never strip `~` — the `~` is OpenRouter's own "latest resolution" alias convention, live-verified, not an opencode artifact); exclude `:free` variants and `~latest` aliases from the servable set by default; derive provider from the catalog (servable-scoped) instead of a provider column; make 429 failover hop-aware (advance only cross-provider) instead of blanket never/always; group the 336-row picker by provider/family and pull the existing Command-pattern search into P1.** The strongest consensus across all files: provider identity is a **catalog lookup, never string surgery** — the v1.3 prefix-strip mapping reused on OpenRouter ids silently swaps providers (`anthropic/claude-sonnet-5` → direct Anthropic, different key/quota/cost), and no code should ever `id.split('/')`, strip `~`, or route on id shape.

The key risks, all mitigated by the recommended decisions: (1) the `anthropic/` prefix collision (PITFALLS 1 — locked by a collision canary + verbatim pass-through); (2) `~latest` alias drift corrupting the `model_used` audit and `:free` shared-account quota turning 50 req/day into a team-wide bottleneck (PITFALLS 2/4 — excluded by the servable rule); (3) OpenRouter error semantics the v1.3 classifier gets wrong or by luck — 402 credits, 502/503 as *model-availability* signals, dual-source 429 (PITFALLS 3/5 — `'billing'` class + hop-aware advance + platform-429 helper); (4) a 336-row flat Select that is unusable and shows duplicate display names across providers (PITFALLS 10 — grouped searchable combobox + provider badges); (5) `OPENROUTER_API_KEY` exposure and company data egress to un-vetted upstream hosts (PITFALLS 11 — server-only key mirroring `ANTHROPIC_API_KEY`, vendor-curated servable set or vendor badges + egress copy).

## Key Findings

### Recommended Stack (from STACK.md — HIGH, live-verified)

The integration is a **drop-in at the existing `anthropic(id)` seam** — `@openrouter/ai-sdk-provider@3.0.0` implements `ProviderV4`, the identical interface to the installed `@ai-sdk/anthropic@4.0.26`, so `openrouter('anthropic/claude-sonnet-4.6')` returns the same `LanguageModel` type `generateText` already consumes. No registry abstraction, no `@ai-sdk/openai-compatible` wrapper, no migration.

**Core technologies:**
- `@openrouter/ai-sdk-provider@^3.0.0` (npm `latest`, published 2026-07-24) — the ONE new runtime dependency. peerDeps `ai ^7.0.0` + `zod ^3.25.76 || ^4.1.8` exactly match installed; engines `node >=22` matches the Vercel pin; zero runtime deps of its own (tarball-verified). **NOT Context7's stale `0.7.5`** (that's the `ai-sdk-v4` dist-tag, AI SDK v4 era) and not the `6.0.0-alpha` prereleases.
- `createOpenRouter({ compatibility: 'strict' })` factory — strict mode is REQUIRED for the real OpenRouter API (default `'compatible'` skips streamOptions); module-scope singleton instance; apiKey auto-loads from `OPENROUTER_API_KEY` when omitted.
- Provider factory `modelFor(id)` / `modelFactory.ts` (new ~10-line module) — the seam replacing `anthropic(id)`: catalog lookup by id → `providerID === 'openrouter' ? openrouter(id) : anthropic(id)`. Zero id collisions between the 17 anthropic and 336 openrouter rows (verified) → provider derivable from catalog, **no `user_model_settings` schema change**.
- `OPENROUTER_API_KEY` — server-only `z.string().optional()` in `env.ts`, mirroring `ANTHROPIC_API_KEY` (D-15 degrade-gracefully); add to `.env.example` + Vercel env.
- **Structured-output caveat:** `Output.object` strict mode is default, but open-source models via OpenRouter may not honor strict JSON-schema — those need `openrouter(id, { structuredOutputs: { strict: false } })` per model (a per-model decision during servable-set curation, never a global default). Response-healing plugin is non-streaming only — not a substitute.

**What NOT to add:** `@ai-sdk/openai-compatible` (loses strict structured-outputs + the catalog's own `api.npm` points at the official package); `createProviderRegistry` (over-engineering for 2 providers); the deprecated `OpenRouter` class export; per-request provider construction; `openrouter/auto` as a default (it's a router, not a model); usage-accounting extras.

### Expected Features (from FEATURES.md — HIGH in-repo, MEDIUM ecosystem UX)

**Must have (P1, all launch-blocking):**
- `providerForModel(id)` + servable-union builder in `catalog.ts` with a Vitest **collision canary** (no id in two servable providers) — the keystone; everything else hangs off it. Must be **servable-set-scoped**, never raw-catalog-scoped (342 ids appear under multiple providerIDs — `claude-sonnet-4-6` exists as opencode AND anthropic; raw first-match returns the wrong provider).
- AI Provider selector above the Primary model — always-valued (default = provider of saved primary; Anthropic when no settings), disabled-with-reason on empty provider catalog, no provider-selected state.
- Provider-scoped Primary picker — on switch, keep-if-valid (one-line guard; de-facto resets since id spaces are disjoint) → reset to the provider's default; draft-only per D-07 with a non-blocking hint; fallbacks untouched by a primary switch.
- Union-scoped fallback pickers — cross-provider chains are a hard requirement; D-08/D-09 dedupe unchanged (id-based); grouping by provider REQUIRED at 337 options.
- Save action widened to the union — zod shape `{ primaryModel, fallbacks }` unchanged (provider derived, never sent by client); 7-case security matrix + atomic upsert untouched.
- Provider-aware instantiation in the run path (`languageModelFor(id)` seam) + per-chain `OPENROUTER_API_KEY` gate (D-15 mirror).
- Per-provider default primary — Anthropic stays `FAST_MODEL_ID`; OpenRouter default chosen during planning.

**Should have (P2):** provider badge on chain entries + audit strip ("which vendor's bill"); family grouping inside the OpenRouter picker (snapshot's `family` field); search/type-ahead in the OpenRouter picker (see Conflict 5 — recommend pulling to P1).

**Defer (v2+):** more providers (OpenAI first-party, Google) — same union machinery, one allowlist entry + one constructor each; provider-scoped cost caps; BYOK for OpenRouter (needs a dedicated security milestone).

**Anti-features:** free-text model id input; provider column on `user_model_settings` (see Conflict 3); BYOK key entry; flat 336-row Select; auto-switch provider from fallback; live-fetching the catalog at runtime; per-provider sub-tabs/wizard.

### Architecture Approach (from ARCHITECTURE.md — HIGH)

Integrates with the existing v1.3 seams rather than creating new foundations. The DB schema is **unchanged** — provider is pure derived state of the committed snapshot, the same philosophy as `getModelDisplayName`.

**Major components (delta):**
1. **Provider registry in `catalog.ts`** (modified) — `ModelProviderId` union, `PROVIDER_GATES` as DATA (anthropic = allowlist, openrouter = full catalog), one parameterized gate `getServableIdsForProvider(catalog, provider)`, `getUnionServableIds`, servable-scoped `getProviderForModelId`. Rename-and-remove `getAllowlistedServableIds` (3 callers + tests).
2. **`modelFactory.ts`** (new module) — `instantiateModel(id)` / `instantiateChain(ids)` / `defaultChain()`; the ONLY module importing provider SDKs (keeps catalog.ts/modelConfig.ts pure and constraint 11 clean); module-singleton `openrouter` instance; throws fail-loud on unknown provider (unreachable post-gate).
3. **`modelConfig.ts`** (modified, small) — `resolveModelChain`'s allowlist param defaults to the union; D-08 dedupe, cap-2, REG-05 default all provider-agnostic.
4. **`analyzeCompany.ts`** (modified) — chain-aware env gate (Pattern 4: every provider in the resolved chain must have its key set, gated ONCE at entry, never per-attempt — per-attempt checks are wrong: missing fallback keys would surface mid-chain with no `not_configured` seam) + factory-based instantiation.
5. **`saveSettingsAction`** (modified, one line + comment) — union validation; `runAgent.ts` (modified, default only); `/settings` page + form (modified); `env.ts` (one line); `schema.ts` **unchanged**.

**Key patterns:** provider→gate map as data; union-filtered chain resolution; provider-aware factory; entry-time provider-set env gate; derive-don't-persist (4 safety arguments: atomic-upsert consistency, third staleness axis, parallel-structure desync, catalog-refresh re-homing).

### Critical Pitfalls (from PITFALLS.md — HIGH)

The one decision that prevents half of them: **`providerID` in the catalog is the ONLY authority for "which provider serves this id" — never derive from the id string — and decide explicitly what the 336 rows reduce to before any UI or run path is written.**

1. **PITFALL 1 — Reusing the v1.3 prefix-strip mapping silently swaps providers (CRITICAL):** `anthropic/claude-sonnet-5` (OpenRouter-proxied) stripped to `claude-sonnet-5` (Anthropic-direct) runs "fine" on a *different product* — different key/quota/cost, and `model_used` records the wrong id. *Avoid:* `resolveProviderForId(id)` catalog lookup only; ids pass through verbatim; never generalize `opencodeSlugToModelId`; collision canary test. **Phase 19.**
2. **PITFALL 2 — `~latest` aliases corrupt the audit and the "trustworthy" promise:** `model_used = "~anthropic/claude-sonnet-latest"` can't say which concrete model answered; cost captions go stale on retarget. *Avoid:* exclude `~`-prefixed ids from the servable set by default (11 rows, zero concrete-pinning value); audits record only concrete ids. **Phase 19 + 21 + 22.**
3. **PITFALL 3 — OpenRouter error semantics don't map to the classifier:** 402 (credits) misclassified as `input`; 502/503 are *model-availability* signals (the purest failover case — must stay `server_error`-eligible, never "fixed"); 429 has two sources (platform vs upstream pass-through) distinguishable only in the response body. *Avoid:* `'billing'` class (never eligible, own reason); comment the 502/503 semantics; `isOpenRouterPlatformRateLimit(err)` helper (verify `APICallError.responseBody` on installed dist first). **Phase 20.**
4. **PITFALL 4 — Free models (`:free`) are a team-wide shared quota:** 20 rpm / 50 rpd account-wide, failed attempts count, SDK retries pile up inside the 54s budget; a `:free` primary 429s → `rate_limited` → never advances → run fails loud. *Avoid:* exclude `:free` from the servable set (or label with quota warning). **Phase 19.**
5. **PITFALL 5 — 429 policy: blanket cross-provider "fix" reintroduces v1.3's resolved bug:** always-advance re-wastes full 12-step agent runs on same-key 429s; never-advance forbids the legitimate Anthropic→OpenRouter hop (different key/account). *Avoid:* hop-aware `shouldAdvance(cls, currentProvider, nextProvider)` — advance on `rate_limited` ONLY when the next entry is on a different provider; 4-cell Vitest matrix; update the stale "429 never advances" docs. **Phase 20 + 22.**
6. **PITFALL 8 — Deriving provider at run time vs persisting it (the milestone's open question):** PITFALLS argues persist-at-save-time (provider column(s), migration, old rows = Anthropic by construction) because derivation breaks exactly when the catalog drifts. **Conflicts with the other 3 files — see Conflict 3; recommendation is derive.**
7. **PITFALL 10 — Provider switch wipes drafts; 336-row picker unusable; duplicate display names:** per-slot provider state vs single selector (see Conflict 6); searchable Command combobox grouped by `family` with provider badges; trim props to `{id, name, cost, family}`. **Phase 21.**
8. **PITFALL 11 — Key exposure + data egress to un-vetted hosts:** server-only key mirroring Anthropic byte-for-byte; vendor-curated servable set (major labs first — 300+ of the 336 rows come from anthropic/openai/google/meta-llama/mistralai/deepseek/x-ai/amazon/cohere/perplexity) or vendor badges + egress copy; the un-curated list includes `openai/o1-pro` at $150/M input. **Phase 19 (key) + 21 (curation/badges) + 22 (security matrix).**

## Conflicts / Open Decisions (planner MUST resolve in requirements)

1. **`~`-prefixed id handling — [RESOLVED, one nuance remains].** FEATURES (Q3) instructed stripping `~` at the instantiation seam and writing the normalized id to audit, based on Context7 examples with unprefixed slugs. **STACK disagrees on live-verified evidence** (the `~` is intrinsic to the API id: `GET /api/v1/models` returns `~anthropic/claude-sonnet-latest`; the unprefixed form does NOT exist — verified). PITFALLS (A/E) and ARCHITECTURE (verbatim pass-through) side with STACK. **Recommendation: pass ALL ids verbatim, never strip.** Nuance: STACK treats the 11 `~` rows as servable (drift caveat); PITFALLS 2 excludes them from the servable set for audit integrity. These are compatible — verbatim pass-through is non-negotiable IF served; the servable-set membership is the open decision (see next item).
2. **`~latest` aliases: servable vs excluded — [OPEN].** STACK: servable verbatim with drift caveat (roster-verify doctrine covers it). PITFALLS 2: **exclude by default** — `model_used`/`model_chain` are the durable-truth contract (D-14), and an alias can't say which model answered; cost captions go stale. **Recommendation: exclude the 11 `~` rows from the servable set for v1.4** (concrete ids only → reproducible audits, honest captions); if product insists, resolve to concrete id at save time via `GET /api/v1/model/{slug}` or label them "always the latest" (PITFALLS E). PITFALLS 2 + Phase 22 assert no `~` in any saved/served value.
3. **Provider column vs derived — [CONFLICT, 3 vs 1].** STACK (zero-collision verified), FEATURES (Q3, servable-scoped + canary), and ARCHITECTURE (Pattern 5, four safety arguments) all say **derive from the catalog, no schema change**. PITFALLS 8 says **persist at save time** (provider column(s); migration while repo is pre-v1.4; run path immune to snapshot drift). Evidence for derive: id spaces are disjoint in the two *servable* sets; the chain-resolution filter drops drifted ids before instantiation (a saved id that leaves the snapshot degrades to the default chain, not a crash); runtime 404→failover is the backstop for live-API removals; no competitor persists provider separately (FEATURES ecosystem analysis); ARCHITECTURE's four invariant/staleness/desync/re-homing arguments. **Recommendation: derive (servable-scoped `getProviderForModelId` + collision canary).** Adopt PITFALLS 8's persist option only if the planner wants zero derivation at run time and accepts a Drizzle migration + third staleness axis.
4. **Cross-provider 429 policy — [CONFLICT, one file has the analysis].** STACK restates D-01 "429 never advances" (correct for same-provider; used to justify free-model fail-loud). PITFALLS 5 is the only file analyzing the cross-provider case: blanket never-advance is now *also wrong* (Anthropic 429 → OpenRouter fallback on a different key/account is legitimate, high-value failover). **Recommendation: hop-aware advance** — `shouldAdvance(cls, from, to)` advances on `rate_limited` only when providers differ; same-provider keeps v1.3 verbatim; OpenRouter→OpenRouter never advances even cross-*model*; platform-level OR 429s (via Pitfall 3's helper) still allow the OR→Anthropic hop. Lock with the 4-cell Vitest matrix. Update stale D-01 docs.
5. **336-row picker: grouping-only P1 + search P2 vs searchable combobox in P1 — [MINOR].** FEATURES (Q5) rates search MEDIUM–HIGH and defers to P2; ARCHITECTURE flags the flat picker as the #1 scaling bottleneck needing "type-to-filter/command pattern OR grouping"; PITFALLS 10 calls the flat 336-row Select unusable and notes the app **already has the Command-based combobox pattern** (explorers' debounced search). **Recommendation: provider + family grouping is the P1 floor (all agree); pull the Command-pattern search into P1** — the marginal cost is low because the pattern is vendored, and it directly de-risks PITFALLS 10's "users can't find a model" failure. Trim server props to `{id, name, cost, family}`.
6. **Fallback-slot UI: single provider selector + union pickers vs per-slot provider selectors — [OPEN].** FEATURES (Q1/Q2): one provider selector above Primary; fallbacks pick from the union, grouped by provider (provider IS the group label); fallbacks survive a primary switch. PITFALLS 10: "per-slot provider state, not one global provider switch" — each fallback slot needs its own provider control. Both enable cross-provider chains. FEATURES matches the milestone's literal wording and is fewer controls; PITFALLS' model is more explicit but adds a control the union picker's grouping already conveys. **Recommendation: FEATURES' model (single selector + union-grouped fallback pickers) with provider badges on every row/chain entry** (the badge delivers the "which vendor" visibility PITFALLS wants); adopt per-slot selectors only if UAT shows the union picker is confusing. Either way, draft preservation is non-negotiable (PITFALLS 10).
7. **Vendor curation / data-egress governance — [OPEN].** Full-catalog (336 rows, incl. 17 single-model vendors + $150/M `o1-pro`) vs trusted-labs-only filter. **Recommendation: ship a vendor-curated servable set (major labs + deepseek/mistralai etc. — the ~300 rows from recognizable vendors) or, if full catalog must ship, vendor badges + explicit egress copy + cost captions.** PITFALLS 11's security matrix adds the key-leak grep.
8. **OpenRouter default primary — [OPEN, pick in planning].** Reset-on-switch needs a defined target. Anthropic: `FAST_MODEL_ID`. OpenRouter: cheapest active concrete slug vs a pinned sensible one (recommend a pinned concrete slug — avoids `~`/`:free`/auto issues and gives stable cost captions).
9. **`structuredOutputs: { strict: false }` per-model pass — [OPEN, pick during servable-set curation].** Identify which servable OpenRouter models can't honor strict JSON-schema; instantiate those per-model. Never global `strict: false` (weakens Anthropic/OpenAI-compatible paths).
10. **`getAllowlistedServableIds` rename — [MINOR].** ARCHITECTURE: remove-and-migrate to `getServableIdsForProvider(catalog, provider)` (3 callers + tests). FEATURES: widen in place. Pick one name; the functional shape is agreed.

## Implications for Roadmap

The four files converge on the same phase skeleton — PITFALLS' pitfall-to-phase mapping (Phase 19 → 20 → 21 → 22), ARCHITECTURE's build order (registry → run path → UI), and FEATURES' dependency graph (union builder → everything) all agree. v1.3 ended at Phase 18, so **v1.4 starts at Phase 19**.

### Phase 19: Provider Registry + Servable Model Source (foundation)
**Rationale:** every other fix composes on the catalog-lookup resolver, the per-provider servable rule, the union builder, and the chain-aware key gate — all pure/testable before any UI or loop change (the repo's Vitest convention). This is where the milestone's open questions get their answers (derive vs persist, `~`/`:free`/vendor servable rules).
**Delivers:** `@openrouter/ai-sdk-provider@^3.0.0` installed (pin `^3.0.0`, verify dist-tags at install — PITFALLS G); `OPENROUTER_API_KEY` in `env.ts` (optional) + `.env.example` + Vercel; `catalog.ts` registry (`ModelProviderId`, `PROVIDER_GATES` data map, `getServableIdsForProvider`, `getUnionServableIds`, servable-scoped `getProviderForModelId`) + collision canary Vitest; **servable-rule decisions** (`~` excluded, `:free` excluded, vendor curation, `strict:false` per-model pass); new `modelFactory.ts` (module-singleton `createOpenRouter({ compatibility: 'strict' })`, `instantiateModel`/`instantiateChain`/`defaultChain`); chain-aware env gate in `analyzeCompany` (per-provider key check once at entry); `saveSettingsAction` widened to union validation.
**Addresses (FEATURES):** `providerForModel` keystone + union builder + canary, provider-aware instantiation, OpenRouter key gate, save-action widening.
**Avoids (PITFALLS):** 1 (prefix-strip collision), 6 (env gate hardcoded), 7 (save validation anthropic-only), 9 (staleness — servable rule removes volatile classes + freshness caption), 11 (key discipline), A (strip `~`), B (kilo/openrouter slug collision), C (`:free`), F (cross-provider gate hole), G (wrong provider version).

### Phase 20: Cross-Provider Run Path (classifier + failover policy)
**Rationale:** depends on Phase 19's resolver + gate; carries the riskiest runtime logic (touches the tested orchestrator). The classifier and 429 policy must be extended *before* cross-provider chains can run safely.
**Delivers:** `classifyModelError` extension — 402 → new `'billing'` class (never failover-eligible, own structured reason "OpenRouter credits exhausted"); 502/503 stay `server_error` with a code comment (model-availability signals on OpenRouter, never "fix" them); `isOpenRouterPlatformRateLimit(err)` body-level helper (verify `APICallError.responseBody` on installed `ai@7` dist + provider first); hop-aware `shouldAdvance(cls, from, to)` + 4-cell Vitest matrix; `runAgent` default → `defaultChain()`; budget notes (OpenRouter proxy latency under the 54s clamp; free-model 3×-backoff pile-up if `:free` ever ships).
**Addresses (FEATURES):** provider-aware run path completion; cross-provider chain execution.
**Avoids (PITFALLS):** 3 (402/502/503/429-body semantics), 5 (429 blanket-fix regression), C (free-tier 429 policy), D (strict structured-output fail-loud — per-model `strict:false` instantiation).

### Phase 21: Settings UI (provider selector + pickers)
**Rationale:** depends on Phase 19; can proceed in parallel with Phase 20 — the UI and the loop are decoupled by the DB + the props-only contract. This is the user-facing payoff of the milestone.
**Delivers:** `/settings` page server-computed per-provider servable lists + union (props trimmed to `{id, name, cost, family}`, catalog.json stays server-only — T-17-09); `ModelSettingsForm`: provider selector above Primary (always-valued, disabled-with-reason on empty provider), provider-scoped Primary picker with keep-if-valid → reset-to-provider-default on switch (draft-only D-07, non-blocking hint, fallbacks preserved), union-scoped fallback pickers grouped by provider (SelectGroup) + family grouping, provider badges on rows/chain entries; per-provider default primary (OpenRouter default from planning); staleness gate union-wide; snapshot freshness caption ("catalog snapshot {generatedAt}"); cost captions incl. the $150/M `o1-pro` warning; **Command-pattern search in the OpenRouter picker (P1 per Conflict 5 recommendation)**; vendor surfacing + egress copy per Conflict 7.
**Addresses (FEATURES):** all table-stakes P1 UI + P2 differentiators (badges, family grouping, search).
**Avoids (PITFALLS):** 2 (no aliases rendered), 4 (no `:free` rendered), 9 (freshness caption), 10 (draft preservation, navigability, dup-name disambiguation), 11 (vendor badges + egress copy), E (alias labeling if aliases ever ship).

### Phase 22: Verification Gate
**Rationale:** the milestone's correctness claims are falsifiable checklists — a dedicated gate, not an afterthought (v1.3's Phase-18 pattern).
**Delivers:** Vitest matrices — collision (`claude-sonnet-5` → anthropic, `anthropic/claude-sonnet-5` → openrouter), 4-cell 429 hop table, error matrix (402 never advances w/ credit reason; 502/503 advance; platform vs upstream 429), servable-rule assertions (no `~`/`:free` id savable or served); end-to-end UAT — save OpenRouter primary → Analyze → `agent_run.model_used` matches (v1.3's core acceptance pattern, now per-provider); OpenRouter-only chain runs with only `OPENROUTER_API_KEY` set; dropped-model 404 → failover (not crash); live-browser provider-switch draft preservation + picker search/grouping + badge disambiguation; security-matrix grep (`OPENROUTER` absent from client components, `NEXT_PUBLIC_*`, action returns); v1.3 same-provider invariants still hold; existing no-`/` invariant tests reworked deliberately, not deleted.
**Addresses:** the full "Looks Done But Isn't" checklist (PITFALLS).
**Avoids:** every pitfall's verification row.

### Phase Ordering Rationale
- **19 before 20 and 21:** the resolver, servable rules, and env gate are independently shippable foundations; both the run path and the UI consume them. The servable-rule decisions (`~`, `:free`, vendor curation) must be locked here or the picker and the gate disagree.
- **20 before 22, 21 parallel to 20:** the classifier + 429 hop policy is the highest-risk runtime change and needs Phase 19's resolver; the UI is decoupled via the DB + props contract and can proceed in parallel.
- **This ordering matches PITFALLS' mapping table exactly** (Phase 19 → 20 → 21 → 22) and ARCHITECTURE's component build order (registry → modelConfig → modelFactory → gate → page/form).

### Research Flags
- **Phase 19:** needs `/gsd-plan-phase --research-phase` only for a **small targeted re-verification at phase start**: `createOpenRouter` strict-compat + structured-output + env-key behavior against the **installed** package (AI-SDK drift discipline — PITFALLS G; the tarball d.ts was verified for this research but re-check post-install). The rest of the phase is fully specified — **skip deep research**. The open decisions (Conflicts 2/7/8/9) are product calls for requirements, not research.
- **Phase 20:** small targeted check, not deep research — confirm `APICallError.responseBody` is populated by the installed provider before writing `isOpenRouterPlatformRateLimit` (PITFALLS 3, AI-SDK drift discipline). Classifier taxonomy otherwise fully specified.
- **Phase 21:** standard patterns (shadcn Select/Command already vendored, Server Actions, props-only contract) — **skip research-phase**.
- **Phase 22:** no research — checklist execution.
