# Phase 4 — UI Design Contract

This phase does not introduce a new visual system — it extends the exact contract already implemented in Phase 2/3 (`02-UI-SPEC.md`, `03-UI-SPEC.md` and the live code in `src/components/companies/`, `src/components/personas/`). Every token below is confirmed against what is actually running in the codebase today, not re-derived. No new user questions were needed: 04-CONTEXT.md's decisions (D-01–D-12) plus the existing Phase 2/3 implementation fully determine this contract. Two of Claude's-discretion items (D-10, D-11) are resolved below with rationale.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | Regular (400) | 1.5 |
| Label | 12px | Regular (400) | 1.4 |
| Heading | 18px | Semibold (600) | 1.2 |

Usage this phase:
- **Heading (18/600/1.2)**: "Related Knowledge" section title — exact same `<h2 className="mb-4 text-[18px] font-semibold leading-[1.2] text-slate-900">` used by every existing section header (Firmographics, Buying Signals, Career History, etc.)
- **Body (14/600 → 400/1.5)**: article title per result — render as `<a>` styled like the existing text-link pattern (`text-[14px] font-normal leading-[1.5] text-indigo-600`, matching the LinkedIn/email link precedent in `persona-detail.tsx:123` and `:135`). Article snippet directly below the title uses Body but in muted color (`text-slate-500`), matching the existing sub-label pattern used under the detail-pane `<h1>` (`company-detail.tsx:51`).
- **Body (14/400/1.5, slate-900)**: detail-pane error-card heading text follows the same weight/size as the list error card's heading, i.e. actually the list error card uses **Heading (18/600/1.2)** for its message, not Body — see Copywriting Contract below; detail-pane error card mirrors that exactly.
- **Label (12/400/1.4)**: article snippet source/meta text if truncation indicator is ever needed (not required by D-06 — title + snippet only, no extra metadata row).

No new size, no new weight, no bold (700) — carried forward unchanged.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Not applicable — Phase 4 is browse/read-only, no page-level CTA button (same as Phase 2/3) |
| Related Knowledge section heading | "Related Knowledge" |
| Related Knowledge — zero matches (D-12) | Section renders nothing — no heading, no empty-state box. Do not show "No related articles found." |
| Related Knowledge — Arcpedia fetch fails (D-10, resolved) | **Silent — section renders nothing**, same treatment as zero matches. Rationale: D-12 explicitly frames "nothing to show" and "couldn't get anything to show" as equivalent from the user's perspective and says the section "shouldn't appear" in either case; extending that same framing to D-10 avoids introducing a second, inconsistent failure-copy pattern for a single small section. | Detail-pane error heading (D-09 — new this phase) | "Couldn't load company" (Company detail) / "Couldn't load persona" (Persona detail) — mirrors `company-list.tsx`/`persona-list.tsx`'s exact "Couldn't load companies"/"Couldn't load personas" pattern, singular since one record is being fetched, not a list |
| Detail-pane error body (D-09) | "Something went wrong fetching this data. Try refreshing the page." — verbatim reuse of the list-pane error body copy |
| Destructive confirmation | Not applicable — no destructive actions exist in this phase |

Note on EXPL-06 scope closure: Phase 2/3 list panes already ship baseline empty/error copy (see `02-UI-SPEC.md` Copywriting Contract). Phase 4's job is (a) extend the identical error pattern to the two detail panes, which currently have zero error handling, and (b) the loading state — both list panes already get a route-level `Skeleton` fallback via `loading.tsx`; detail panes ride the same `loading.tsx` (single Suspense boundary per route covers list+detail together, confirmed in `companies/loading.tsx`/`personas/loading.tsx`) so no new loading copy/skeleton is needed for the detail pane's DB fetch. ## Interaction Notes (D-11 — Suspense/streaming, resolved)

**Decision: no new Suspense/streaming boundary this phase.** The Arcpedia `fetch()` call runs inside the same `async` Server Component as the rest of the detail pane (`CompanyDetail`/`PersonaDetail`), so it is covered by the existing route-level `loading.tsx` skeleton exactly like every other awaited call in that component tree (DB queries included) — no new pattern introduced, consistent with D-04/D-09's stated bias toward reusing what Phase 2/3 already built. This is a default, not a hard lock: if `04-RESEARCH.md` finds Arcpedia's `/api/wiki/search` has real-world latency that visibly delays the whole detail pane behind the DB fetch, revisit and introduce a dedicated `<Suspense>` boundary around only the Related Knowledge section (streaming it in after the rest of the pane) — flag this explicitly in the plan if research surfaces a concrete latency number.

**Fetch call shape:** server-side `fetch('https://arcpedia.arclumen.de/api/wiki/search?q=<entity name>')` inside the detail pane's Server Component (no client-side hook), matching the "Server Components fetch directly" convention already established for DB queries. Response shape (confirmed via `arcpedia/src/lib/search.ts` `ContentSearchResult`): `{ results: Array<{ slug, title, summary, snippet, score, fuzzy? }> }`. D-06's "title + snippet" render uses `title` and `snippet` directly from this shape — no additional Arcpedia lookup needed. Cap the rendered list at the first 3 results per D-08 (Arcpedia's own `maxResults` default is 10 — truncate client-side/server-side to 3, don't rely on an Arcpedia query param to do it).

**Link target:** `https://arcpedia.arclumen.de/wiki/<slug>`, `target="_blank" rel="noopener noreferrer"` — exact precedent from `persona-detail.tsx`'s LinkedIn link (D-07).
