### Runtime reproduction — 2026-08-07
- Command: guarded `db:push`, schema metadata integration, then `analysisResults.integration.test.ts`; `.env.local` was loaded in-process and only command-scoped `DATABASE_URL`/`TEST_DATABASE_URL` were assigned.
- Observed: `db:push: PASS`; `schema metadata: PASS`; `packet integration: FAIL`.
- Exact database error: `Caused by: NeonDbError: column "status" is of type analysis_evidence_status but expression is of type text`.
- Exact database code/hint: `code: '42804'`; `hint: 'You will need to rewrite or cast the expression.'`.
- Interpretation: the authoritative CTE reaches PostgreSQL with JSON `text` for the enum-bound finding columns; schema and connectivity are not the failing boundary.

### Red phase — 2026-08-07

- Confirms: the regression fails against the unchanged CTE because neither JSON-derived enum expression is explicitly cast.

### Follow-up runtime evidence — 2026-08-07
- After the required status/confidence casts, guarded `db:push` still passed, but the real schema + pure query + packet integration gate reported `1 failed | 2 passed` files and `2 failed | 10 passed` tests.
- Exact database error: `Caused by: NeonDbError: column "classification" is of type analysis_source_classification but expression is of type text`.
- Exact database code/hint: `code: '42804'`; `hint: 'You will need to rewrite or cast the expression.'`.
- Interpretation: the same authoritative CTE contains two additional JSON-to-enum assignments (`analysis_source.classification` and `analysis_finding_source.support_role`) that PostgreSQL validates before row production; leaving either uncast would keep both real packet cases red.

### Follow-up runtime evidence — 2026-08-07
- After all JSON-derived enum assignments were cast, the real packet integration still failed in both cases with `Error: analysis packet persistence returned no result` (`2 failed | 2` tests); no database error was emitted.
- Interpretation: the initial insert path reaches the final CTE result guard without a row. The final `SELECT` reads `analysis_run_result` in the same data-modifying CTE statement instead of returning the `inserted_result` row directly, so the initial insert result is not visible through that base-table read.

### Root cause confirmed — 2026-08-07
- Mechanism: JSON operators return `text`; PostgreSQL does not implicitly assign that text to the declared status, confidence, source-classification, or support-role enum columns. Once those casts were added, the initial data-modifying CTE still returned no authoritative row because its final base-table read could not see the newly inserted row in the statement snapshot.
- Toggle proof: without the enum casts, Neon returned `42804`; with the casts, Neon reached the result-return path. Without direct `inserted_result` selection, both integration cases returned no result; with the direct insert branch and replay fallback, both cases passed.
